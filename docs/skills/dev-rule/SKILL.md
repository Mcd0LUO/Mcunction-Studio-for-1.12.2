# 开发流程规范（自然语言版）

本规范适用于代码生成、迭代开发和修改维护等所有开发活动。它定义了从项目启动到缺陷处理的完整生命周期，明确了不同决策的权限归属，并严格约束了主代理与子代理之间的协作方式。请所有开发参与者严格遵守。

---

## 一、项目生命周期节点

### 1. 项目初始化
- 在项目根目录下创建 `docs/` 文件夹，并在此目录中生成完整的核心文档，包括：
  - 项目定位与目标
  - 整体架构设计
  - 开发路线图（里程碑）
  - 依赖清单（外部库、服务等）
- 所有后续生成的文档（如计划、报告）也统一存放于 `docs/` 下。

### 2. 迭代前规划（每个迭代开始前）
- 必须产出 `plan.md` 文件，内容需包含：
  - **复杂度评估**：低 / 中 / 高
  - **涉及模块**：明确本次改动影响哪些模块或组件
  - **验收标准**：可验证的完成条件（如测试通过、性能指标等）
  - **Token 预算**：预估消耗不得超过当前上下文容量的 **30%**（用于控制成本）

### 3. 缺陷处理
- 一旦发现缺陷（包括自测、评审或用户反馈），立即在 `bugs/` 目录下创建缺陷记录文件。
- 每条缺陷记录必须包含以下字段：
  - **等级（P0~P3）**：P0 为最高紧急（阻塞发布），P3 为建议修复
  - **定位**：问题发生的模块、文件或函数
  - **解决方案**：修复思路或临时规避措施
  - **状态**：open（待处理）或 fixed（已修复）

### 4. 状态报告（重大变更后）
- 每当完成一次重大变更（如版本发布、架构调整、核心功能上线），需生成状态报告。
- 报告文件命名格式：`status/[YYYY-MM-DD]-<版本号>.md`，内容应总结变更内容、影响范围、后续计划等。

## 二、决策权限与执行规则

### 1. 重大决策（需用户确认）
  以下类型的变更属于**重大决策**，**绝对禁止**代理自行执行，必须先记录到 `actions/` 目录下的决策文件中，并挂起等待用户明确批准：

- 数据库切换（如从 MySQL 改为 PostgreSQL）
- API 契约变更（修改请求/响应格式、字段删除等）
- 批量删除文件（超出单个文件的操作）
  
  处理方式：创建 `actions/<描述>.md`，说明变更理由、影响范围和具体操作，然后通知用户审批。在获得“确认”指令前，不允许执行任何代码修改或环境变更。
  
  ### 2. 次要决策（自主执行）
  以下细节类决策属于**次要决策**，代理可按行业最佳实践直接执行，无需用户确认，但须在 `plan.md` 的备注中简要记录所做选择：

- 变量命名风格（采用驼峰还是下划线）
- 代码缩进与格式化（遵循项目已有风格）
- 局部变量抽取（提升可读性，不改变逻辑）

### 3. 失败重试机制
- 任何操作（如构建、测试、文件读写）若失败，允许自动重试，但**最多重试 3 次**。
- 若 3 次后仍然失败，必须**立即中断**当前流程，将任务状态标记为 `AWAIT_USER`（等待用户介入），**禁止**代理自行重新评估架构或修改策略。

## 三、主从代理协作规则

### 主代理（Master）职责
- **禁止编写任何业务代码**——主代理只负责任务拆分、分发和结果合并。
- 分发任务给子代理时，指令必须**精确**，包含：
  - 目标文件路径
  - 具体行号或函数签名（若适用）
- **禁止**附带子代理不需要的无关代码全文，以保持通信轻量。

### 子代理（Sub‑agent）输出格式
- **成功时**：仅输出纯代码块（允许包含原生注释），**不允许**附带任何自然语言描述（如“修改完成”、“已处理”等）。
- **失败时**：输出极简错误信息，**严格限制英文且不超过 15 个单词**，例如：`ERROR: File not found` 或 `ERROR: Compilation failed`。

---

## 四、其他约定
- 所有文档（计划、报告、行动记录等）均使用 Markdown 格式。
- 任何未在上述规则中明确的事项，遵循“先记录、后询问”原则，避免擅自行动。

---

**本规范为强制性执行标准，适用于所有开发环节。如有疑问或需调整，请先与项目负责人沟通。**
