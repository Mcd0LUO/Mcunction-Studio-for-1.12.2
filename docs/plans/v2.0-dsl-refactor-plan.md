# 重构计划：命令构造器链式 DSL 全量重构

> **日期**: 2026-06-20
> **复杂度**: ⭐⭐⭐⭐⭐ (最高级 — 全量重构)
> **目标版本**: v2.0.0

---

## 一、背景与动机

### 现状问题

1. **命令补全逻辑难以维护**：48+ 个命令 Provider 各自在 `provideCommandCompletions` 中用深层嵌套 if/else 手写补全逻辑。每加一个子命令需阅读数百行代码才能定位修改点。

2. **命令结构与补全生成脱节**：命令定义（子命令/参数/选项）隐含在补全代码中，无法从代码直接看出命令语法结构。

3. **动态加载脆弱**：`CommandRegistry.autoRegisterProviders` 使用 `import()` + 文件名约定动态加载，TypeScript 编译后路径依赖不稳定。

4. **签名帮助重复编码**：`Signature.ts` 中每个命令单独手写 `SignatureHelp`，与补全逻辑重复表达同一命令结构。

5. **单例全局状态**：DataLoader、MacroManager 等使用单例，模块间隐式耦合，难以测试。

6. **巨型文件**：EnumLib.ts (1677行)、DataLoader.ts (790行)、Base.ts (476行) 职责过多。

### 目标

采用**命令构造器链式 DSL** 统一定义命令结构，**自动派生**补全、签名、校验功能：

```typescript
// 一条命令定义 → 同时获得 补全 + 签名帮助 + 校验
const scoreboard = buildRootCommand("scoreboard")
  .description("管理记分板系统")
  .subcommand(
    buildSubCommand("objectives")
      .desc("管理记分项")
      .subcommand(buildSubCommand("add")
        .positionalArg(buildPositional("name").required(true))
        .positionalArg(buildPositional("type")
          .suggest(ctx => MinecraftStats.all.map(s => s.name)))
      )
      .subcommand(buildSubCommand("remove")
        .positionalArg(buildPositional("name")
          .suggest(ctx => ctx.index.getScoreboardNames()))
      )
  )
  .subcommand(
    buildSubCommand("players")
      .desc("管理玩家记分板数据")
      .subcommand(buildSubCommand("add")
        .positionalArg(buildPositional("target").suggest(selectorSuggest))
        .positionalArg(buildPositional("objective").suggest(scoreboardSuggest))
        .positionalArg(buildPositional("value"))
      )
      // ...更多子命令
  )
  .build();

registerCommand(scoreboard);
```

## 三、技术方案

### 3.1 DSL 命令节点类型

```typescript
// 命令语法节点类型
type CommandNode = RootCommandNode | SubCommandNode;

interface RootCommandNode {
  kind: 'root';
  name: string;
  description: string;
  flags: FlagDef[];
  children: SubCommandNode[];
}

interface SubCommandNode {
  kind: 'subcommand';
  name: string;
  description: string;
  flags: FlagDef[];
  options: OptionDef[];
  positionalArgs: PositionalDef[];
  children: SubCommandNode[];  // 嵌套子命令
}

interface FlagDef {
  name: string;
  short?: string;
  long?: string;
  description: string;
}

interface OptionDef {
  name: string;
  short?: string;
  long?: string;
  takesValue: boolean;
  description: string;
  suggest?: SuggestFunction;
}

interface PositionalDef {
  name: string;
  required: boolean;
  suggest?: SuggestFunction;
}

type SuggestFunction = (ctx: CompletionContext) => CompletionItem[];
```

### 3.2 补全生成算法

```
输入: 用户已输入的命令片段 [c1, c2, c3, ...]
输出: CompletionItem[]

算法:
  1. 从根命令树查找 c1 匹配的 RootCommandNode
  2. 沿树向下遍历，匹配 c2, c3, ... 到对应的 SubCommandNode
  3. 到达当前最深匹配节点 N:
     a. 收集 N.children 中的子命令名 → CompletionItem[]
     b. 收集 N.positionalArgs 中当前阶段参数的 suggest → CompletionItem[]
     c. 收集 N.flags / N.options → CompletionItem[]
  4. 返回合并结果
```

### 3.3 签名生成算法

```
输入: 用户已输入的命令片段 [c1, c2, ...]
输出: SignatureHelp | null

算法:
  1. 在命令树中定位当前节点
  2. 构建参数签名列表
  3. 计算当前活跃参数索引
  4. 返回 SignatureHelp
```

### 3.4 兼容 execute/detect 嵌套

`execute` 命令的特殊之处在于它包含子命令。DSL 需要表达：

```typescript
buildRootCommand("execute")
  .subcommand(
    buildSubCommand("<selector>")      // 隐式子命令（实体选择器）
      .positionalArg(buildPositional("target").suggest(selectorSuggest))
      .positionalArg(buildPositional("x"))
      .positionalArg(buildPositional("y"))
      .positionalArg(buildPositional("z"))
      .subcommand(buildSubCommand("detect")  // detect 子修饰符
        .positionalArg(buildPositional("dx"))
        .positionalArg(buildPositional("dy"))
        .positionalArg(buildPositional("dz"))
        .positionalArg(buildPositional("block"))
        .positionalArg(buildPositional("data"))
        .subcommand(...)  // 可继续嵌套任何命令
      )
      .forward()  // ← 关键：forward() 表示 execute 后面可以跟任何子命令
  )
```

`forward()` 方法标记该位置接受所有已注册的根命令作为子命令。补全引擎遇到 `forward` 节点时，返回到根命令列表的补全。
